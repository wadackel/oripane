# Oripane development guide

A Mac display streamed to an Android phone (a Galaxy Z Fold) over the LAN or Tailscale, as a
second display, a mirror, or a mirror reshaped to the phone (Match). `README.md` introduces it to
a first-time visitor; `docs/usage.md` is the user's guide and `docs/development.md` how the
repository is built and tested; `docs/protocol.md` is the wire contract both sides implement; `docs/design.md` is the design
language every Android screen follows, and a UI change that needs a rule it lacks adds the rule there.
`docs/security.md` says what Oripane protects, and `SECURITY.md` treats a mismatch with it as a
vulnerability: a change to pairing, keys, what a phone can do on the Mac, or what is logged updates it.

## Rules that are easy to break

- **A wire change lands in four places at once**: `docs/protocol.md`, `host/Sources/OripaneCore`,
  `android/protocol`, and `spec/vectors.json`. The vectors are generated by the host
  (`oripane-host vectors spec/vectors.json`) and the Kotlin `VectorsTest` checks its own encoders
  against them byte for byte; `tools/test` fails when the regenerated file differs from the
  committed one. Never edit the JSON by hand. Control messages are JSON built where they are
  sent (`StreamHost`, `StreamClient`) and are not in the vectors: a new field there lands in
  `docs/protocol.md` and both implementations.
- **Every virtual display create and release goes through `StreamHost.enqueue`.** Creating one
  while another is being released, or releasing one whose mode is not settled yet, aborts
  WindowServer (`GenerateModeListForDisplay` in SkyLight) and takes the owner's whole session
  down. A resize during a session reconfigures the display; it does not recreate it.
- **The host runs inside `NSApplication`'s event loop** (`runApplication` in `main.swift`). With a
  bare run loop or `dispatchMain()` no display reconfiguration callbacks arrive, and CoreGraphics
  never learns the modes of a virtual display the process created itself.
- **`CGVirtualDisplay` is private API**, declared in `host/Sources/CVirtualDisplay`. After a macOS
  update, check it alone before connecting a phone:
  `for step in create stream resize recreate match; do tools/host display-check $step || break; done`.
- **Each host component owns one serial queue**, and the package stays in Swift 5 language mode.
  Strict concurrency fights the callback APIs (SCStream, VTCompressionSession, Network.framework)
  the host is built from.
- **`android/protocol` is a plain JVM module.** It is what the vectors test runs against without a
  device; an Android import there means the code belongs in `:app`.
- **The four nonce directions never share a counter space** (`dir` byte in Session crypto). A new
  encrypted stream gets a new direction, not a reuse of an existing one.

## Verifying a change

`tools/test` runs every automated check: Swift core tests, the vectors, the Kotlin tests with the
screenshot comparison, and a debug APK build; `tools/test --help` lists its partial runs. Run
checks through it rather than `swift test` or `./gw` by hand (recording screenshots excepted):
both pass a filter that matches no test, which `tools/test` fails. The devShell points
`DEVELOPER_DIR` and `SDKROOT` at nixpkgs' Apple SDK, which hides `/usr/bin/swift`. Run `tools/app`
and a hand-typed `swift` outside the devShell or under `env -u DEVELOPER_DIR -u SDKROOT`; the
other `tools/` scripts work either way.

Only a local `tools/test` compares the screenshots of every page and sheet with the committed
images, pixel for pixel; CI runs the same tests without comparing, since it renders on other
machines. A change meant to alter how the app looks records them again and commits the new images
in the same pull request; the command is in the KDoc of `Screenshots.kt` in the app's tests. The
README's pictures in `docs/images/` come from `DocsScreenshotTest` and are recorded and compared
with them: open the changed ones to check they still show what the README says.

CI splits this by cost. A pull request that touches `android/`, `spec/` or `LICENSE` runs the Kotlin tests
and the debug APK build on Linux (`.github/workflows/android.yml`); a push to `main` that touches
them runs the same job to refresh the Gradle cache the pull requests read. A push to `main` that
touches `host/`, `spec/`, the flake or `tools/test` runs `tools/test` on a macOS runner
(`.github/workflows/test.yml`), so a Swift failure shows up after the merge. Run `tools/test`
yourself before merging a change to `host/` or `android/`; after merging one to `host/`, check
that push's run with `gh run list --workflow test.yml`.

For the running system, start with the emulator and a test host, which leave the owner's
Oripane.app alone. The scripts are `tools/emu`, `tools/eadb` (adb that reaches only the
emulator), `tools/ui` (what the emulator's screen shows, and taps on it) and `tools/testhost` (a
host that streams the test pattern on a port of its own); `tools/emu connect <mode> <port>`
points the app at that port. Without a port, `tools/emu connect` reaches the owner's Oripane.app
and shows the owner a pairing dialog. Their usage is in the scripts. The host's test options and
environment variables (packet loss, a forced codec, faked failures, the headless `probe` client)
are in `tools/host --help` (the `oripane-host` usage).

adb's own mDNS crashes the adb server on this Mac (an abort inside `adbmdns_bridge` about a minute
after start), and every adb command then fails with "device not found". An adb command that finds
no server starts one with mDNS, `tools/eadb` and so `tools/emu` included: before the first one,
start the server yourself as a background task with `ADB_MDNS=0 adb nodaemon server`. If one
already runs with mDNS (`tools/phone status` says so), run `adb kill-server` first.

Both sides log one `event key=value` line per event: the host to stderr, the app to
`adb logcat -s oripane`. The `stats` lines carry fps, latency, loss and repaired frames.

### On the owner's phone and Mac

The physical phone and this Mac are the owner's own devices, so a test there touches real state:

- Without `--dry-run-input`, taps on the phone click and type on the owner's Mac. Keep the flag
  unless the owner asked for real input.
- Extend mode adds a display to the Mac until the session ends or switches to mirror. Match adds
  one too and makes the main display mirror it. Stop the host with SIGINT or SIGTERM, never
  SIGKILL: its shutdown ends the mirroring and releases the display.
- **The Fold runs the release build, and the owner uses it every day.** Put a build on it only
  with `tools/phone install`, which also reinstalls Oripane.app when the Mac's build is behind.
  Before every run, show the owner, here in the conversation, the plan that
  `tools/phone install --dry-run` prints, and wait for their yes to it, even after an earlier yes
  in the same session.
  When the plan refuses a build that is not an ancestor of HEAD, the owner's yes to that plan,
  `refuse` line included, also covers `--allow-diverged`. The tool has no prompt of its own,
  because an agent could answer one itself. Its `status` and `--dry-run` only read, and need no
  question.
- `tools/host run` asks for `y` on its stdin. Without a terminal, feed stdin from a fifo and
  approve only after the code on the phone matches the host's log line. `--auto-approve` is for
  the emulator.
- The owner normally runs the host as the menu bar app `~/Applications/Oripane.app` (`tools/app`,
  `docs/usage.md` "On the Mac"), which holds ports 47800/47801 and the owner's pairings. `tools/host run` and
  a test copy of the app (which hands off to the running one) need it quit first, unless the
  `tools/host run` takes another `--port` and its own `ORIPANE_STATE_DIR`: on the default state
  dir, either host rewrites the pairings file over the other's changes. Quitting it cuts the
  owner's phone off: ask the owner before `tools/app quit`, and open it again afterwards
  (`tools/app open`). `tools/testhost` does both and needs neither the quit nor the question.
  Apart from `tools/phone install`, run `tools/app install` or `uninstall` on
  `~/Applications/Oripane.app` only when the owner asks: `install` replaces the app the owner's
  privacy grants and login item belong to.
- A test copy, for checking the menu bar app itself (its menu, its pairing dialog), is the
  installed app opened with test options, its own state and log, and a port away from the
  owner's; it then asks for no permission and leaves the owner's pairings alone:
  `open -n --env ORIPANE_STATE_DIR=$(mktemp -d /tmp/op.XXXX) ~/Applications/Oripane.app --args
  --source test --dry-run-input --no-bonjour --port 47900`. Its log is `<state dir>/host.log`.
  Pairing requests appear as a dialog, which System Events can read and press; its SwiftUI
  buttons have no readable title, so press by position (Deny left, Allow right) and check the
  `ui pairing_dialog answer=` log line.
- `tools/host probe` reaches 127.0.0.1:47800 unless given `--port`, and pairs at once; there it
  meets the owner's Oripane.app, which shows the owner a pairing dialog. Point it at a test host.
- `tools/app install` signs with a self-signed certificate in its own keychain
  (`~/Library/Keychains/oripane-signing.keychain-db`). Never delete or recreate it: every grant
  the owner gave is tied to that certificate.
- A static desktop produces no frames, because ScreenCaptureKit only delivers changes. `fps=0` on
  an idle screen is not a stall.

Reaching the phone:

- `tools/phone` finds the phone and connects to it over wireless debugging, on the adb server
  started as above; `tools/phone status` prints the address adb reaches it at.
- **The Fold has two displays.** When folded, logical display 0 is the cover screen and display 1
  is the inner one, switched off. `input` takes the logical id (the default is right); `screencap`
  needs the physical id from `adb shell dumpsys SurfaceFlinger --display-id`.
- **Turning the phone's Wi-Fi off drops wireless debugging with it.** To test the route away from
  home, keep adb on the tailnet first:

  ```sh
  adb -s <phone-lan-ip>:<port> tcpip 5555               # the address tools/phone status prints
  adb connect <phone-tailnet-ip>:5555
  adb -s <phone-tailnet-ip>:5555 shell cmd wifi set-wifi-enabled disabled
  # … observe …
  adb -s <phone-tailnet-ip>:5555 shell cmd wifi set-wifi-enabled enabled
  adb -s <phone-tailnet-ip>:5555 usb                    # closes port 5555 again
  ```

## Merging a change

Every change goes through a pull request. What approves the merge depends on whether the owner
has to feel the change on the phone:

- **Nothing to feel**: tools, tests, docs, `--help`, a refactor whose screenshots show no
  difference. Once CI, where it runs, and the review (`/gate`) pass, merge it without the owner,
  even when the gate lists hunks for human review.
- **Something to feel**: gestures, thresholds, how a page or the stream looks or responds. Once
  CI passes where it runs, install the release build on the Fold with `tools/phone install`,
  asking the owner first as above, and let the owner try it. The owner's OK after trying it
  approves the merge.

When it is unclear which kind a change is, treat it as something to feel.

## Conventions

- Code, comments, `docs/`, `README.md` and this file are in English.
- Comments explain why an obvious alternative was rejected. They do not restate the code or record
  the conversation that produced them.
- Swift tests use swift-testing and Kotlin tests JUnit 4 with Truth; test names describe the
  behaviour, not the method.
- A Kotlin file under `src/main` opens, before its `package` line, with a KDoc that says what the
  file holds, by its role rather than as a list of its declarations. A file gains one when it is
  created, including by splitting another file, and a file that has one updates it when what it
  holds changes. File names and these KDocs stand in for a map of the code; this guide is not one.
