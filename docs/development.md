# Development

How Oripane is built, run and tested. Everything here assumes the owner's setup: one Mac that both
builds and hosts, a Galaxy Z Fold, [Nix](https://nixos.org/download/) with flakes, and the Android
SDK at `~/Library/Android/sdk`. Pull requests from outside are not accepted, so the scripts are not
made to work anywhere else; read them as a record of how this repository is worked on. Rules for an
AI agent working here are in [`AGENTS.md`](../AGENTS.md).

## How it works

```
[Mac]      virtual display → ScreenCaptureKit → VideoToolbox (low-latency HEVC, or H.264 for a phone without HEVC hardware)
           → UDP (fragments + XOR parity + AES-GCM)  ~~ Wi-Fi / Tailscale ~~
[Android]  reassembly + FEC repair → MediaCodec → SurfaceView
           touch and keys → UDP / TCP → CGEventPost on the Mac
```

| Directory | Contents |
|---|---|
| `host/` | The Mac side (a Swift package that builds with the Command Line Tools alone) |
| `android/` | The Android side (`:app`, and `:protocol`, which runs on the plain JVM) |
| `docs/usage.md` | How to set up and use both sides |
| `docs/protocol.md` | The wire protocol |
| `docs/security.md` | What is protected, where the keys are kept, and what is never logged |
| `docs/design.md` | The design language every Android screen follows |
| `docs/images/` | The README's pictures and the social preview, rendered by a test (below) |
| `spec/vectors.json` | Test vectors that check both implementations agree byte for byte (generated by the Mac side) |
| `tools/` | Scripts to build, run and test, and to drive the emulator |

## Running the host from a terminal

```sh
tools/app quit                  # the app holds port 47800, so quit it first
tools/host run                  # wait for the phone, in the mode the phone chooses
tools/host run --mode mirror    # always mirror
tools/host run --mode match     # always match
tools/host pairings             # the paired phones
```

- The terminal it runs in needs the Screen Recording and Accessibility permissions. Without Accessibility, input is only logged and never reaches the Mac.
- When a new phone connects, the terminal prints `Pairing request: the phone must show 123456`, the requesting phone's name, where the request came from (this Mac, an address on the LAN or on Tailscale) and `Pair? [y/N]`. Answer `y` if the code matches the one on the phone. A request that comes meanwhile waits its turn, an answer typed within a second of its question is asked again, and an address answered with anything but `y` is refused for 30 seconds.
- `--source test` streams a synthetic pattern instead of the screen. `--drop 0.05` drops 5% of outgoing packets, to watch FEC and keyframe requests at work. `tools/host --help` lists every option and the environment variables for testing.
- When done, open the app again with `tools/app open`.

## The virtual display

The virtual display is created with a private API (`CGVirtualDisplay`). Running a create and a release at the same time is confirmed to crash WindowServer (releasing a virtual display while another one has no settled mode aborts SkyLight's `GenerateModeListForDisplay`). The host lines up every create and release in one serial queue, and a resize during a session reconfigures the display instead of recreating it.

The host runs in `NSApplication`'s event loop. With a bare run loop, no display reconfiguration notifications arrive, and the modes of a virtual display the process created itself stay invisible.

After a macOS update, the virtual display can be checked step by step on its own before connecting a phone:

```sh
for step in create stream resize recreate match; do tools/host display-check $step || break; done
```

## Testing

```sh
tools/test                             # Swift unit tests, the vectors check, the Kotlin tests with the screenshot comparison and an APK build
tools/test host --filter TailnetTests  # one step, filtered (tools/test --help)
ADB_MDNS=0 adb nodaemon server &       # adb's own mDNS crashes the adb server on the owner's Mac
tools/emu start                        # boot a foldable AVD headless
tools/emu install
tools/testhost run                     # in another terminal: a host streaming a test pattern on port 47940; Oripane.app keeps running
tools/testhost wait                    # until it listens (run builds the host first)
tools/emu connect extend 47940         # connect from the emulator to that host (10.0.2.2:47940); pairs the first time
tools/ui list                          # the labels on the emulator's screen; tools/ui tap <label> taps one
tools/emu shot /tmp/shot.png
tools/testhost stop
```

`tools/eadb` is adb pinned to the emulator, so nothing gets installed on a real phone by mistake.

`tools/emu connect` without a port reaches Oripane.app on 47800 instead, and the first time it asks for pairing on the Mac's screen.

Only a local `tools/test` compares the screenshots in `android/app/src/test/screenshots/` with the app, pixel for pixel; CI runs the same tests without comparing. After changing how a page looks on purpose, record them again (the command is at the top of `Screenshots.kt` in the app's tests) and commit them with the change.

## Documentation screenshots

The images in `docs/images/` are rendered by a unit test, `DocsScreenshotTest`, on the JVM through
Robolectric's native graphics. The line drawing at the top of the README, one image for GitHub's
light theme and one for its dark theme, and the social preview (`social-preview.png`, 1280 × 640)
are drawn on a canvas (`DocsArt` in the app's tests). The feature pictures are the app's own
screens with fixed sample data; the Mac on them is a desktop drawn from shapes (`MacDesktop`) in
place of the video. No emulator, host or real desktop is involved, and they come out the same on
every run. GitHub does not read the social preview from the repository: it is uploaded by
hand under Settings → General → Social preview.

They are recorded and compared with the other screenshots: the command in `Screenshots.kt` records
them too, and a local `tools/test` fails when a screen in the README no longer matches its image.
After such a change, record them again, open the changed images, and commit them with the change.
